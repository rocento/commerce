## Internal enrollment and publishing verification — 2026-10-12

Deployed and verified against production dashboard/native APIs. The App Studio **Test installations** panel is owner-only and uses the mobile administration host. New runtime enrollment/session/asset endpoints remain blocked on that host; native apps use their compiled grocery API origin. No core admin pages or customer session credentials are involved.

An owner issues a random 64-character code for a pre-provisioned production app identity. The code expires in 15 minutes, is stored hashed, and can be consumed once. Enrollment checks the issuer's current owner membership, active merchant and identity, platform, merchant and application identifier inside a transaction. Matching identifier strings alone do not authenticate an app. This is a controlled internal-testing connection, not App Attest/Play Integrity or public consumer onboarding.

Both apps expose **Account → App connection**. The device-only Keychain/Keystore entry uses the independent `config-device` purpose. A device credential lasts 30 days; its access session lasts 30 minutes, remains in memory and is renewed before expiry. Renewal replaces prior access without rotating or extending the device credential, so a lost renewal response can be retried. Owner revocation disables sessions, renewal and future private asset delivery. Previously downloaded nonsecret configuration remains available offline. Commerce/customer sign-in is independent.

Private PNG reads require an active native session and an asset reference in the latest compatible published configuration. Draft-only, foreign and unverified assets are denied. Storage keys are constructed from the authenticated merchant and asset, never supplied by the caller. Backend and clients verify exact-byte SHA-256 checksums. Asset responses are private/no-store, have no redirects, and carry no customer bearer. Rendering uses bounded thumbnails. Trusted legacy external asset URLs are not proxied by this endpoint.

## Account onboarding refinement — 2026-10-12

The iOS and Android Account screens now present separate sign-in, create-account,
verification, forgot-password and reset-password steps. Registration moves to
verification after the server succeeds; verification and password reset return to
sign-in. Recovery requests use an account-neutral acknowledgement. Failed requests
keep the current step and entered values for retry. Switching steps clears passwords,
confirmation and challenge tokens. Secrets are held in transient view state, never
saved as form preferences.

New-password confirmation and UTF-8 byte-length validation match the service's
12–128-byte policy; sign-in accepts existing passwords without imposing a new-password
rule. Verification and reset require a nonblank challenge token. The service continues
to enforce identity validity, challenge expiry, rate limits and session authorization.
Both platforms provide English/Arabic instructions, password visibility controls,
stable accessibility/test identifiers and disabled submission during requests. Existing
secure credential storage, session renewal, saved addresses, order history and sign-out
remain in use. No backend API or production deployment is required for these UI changes.

Regression coverage includes multibyte passwords, confirmation mismatches, blank
identifiers/codes, successful next-step selection, and native registration → verification
and recovery → password-reset flows with isolated transports. Evidence is in
`output/mobile-account-20261012/`. Delivery of real verification/reset messages and
signed physical-device acceptance remain part of the existing release gates above.

### Native shopping assistant — implementation, 2026-10-12

The production native targets now share the existing commerce gateway's assistant
API. The [mobile implementation notes](native-runtime-2026-10-12.md#native-shopping-assistant--2026-10-12)
cover native chat, product cards and product selection, comparisons, clarifications,
cart refresh, reviewed basket approval and checkout navigation. AI execution and
commerce authority remain on the server. This change introduces no new endpoints,
config fields, migrations or backend/frontend deployment requirements.

Only a validated `message.delta` checkout command followed by a successful `done`
opens checkout. Plain text, failed streams and restored UI content cannot submit
orders or trigger checkout. Customer session changes reset native chat, request
streams are bounded/cancellable, and a rejected HTTP 401 may refresh authentication
once before retrying; partial responses never retry automatically. Cart data is
refreshed after completed or interrupted turns because a server cart action may have
committed before disconnection. Conversation content remains in memory for the app
session; background streaming and native history browsing are separate work.

The assistant's shared wire fixture is validated against the canonical OpenAPI.
Swift and Kotlin unit tests and isolated UI scenarios are included. Combined runtime
1.2 installation and actual simulator/emulator UI execution are owned by the coordinated
release verification; this source change does not itself publish or install apps.
