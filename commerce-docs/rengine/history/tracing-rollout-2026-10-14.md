## Before deployment

- Confirm gateway compatibility with reports v1/v2 and the matching rengine reader.
- Resolve packaged language-release compatibility: the checked-in Python/Node wire fixtures lack the recognition snapshot expected by the current engine. The temporary recognition fixture used for tests changes its fingerprint, so it must not be substituted for the deployed release. Python must continue to reject an incompatible release.
- Agree the numeric capture overhead budget on a representative workload. Existing local microbenchmarks are not a production latency budget.
- Select one demo, an authorized tracking operator, and a synthetic read-only question that executes language resolution and a catalog read. No production credentials or customer payloads belong in validation artifacts.

## One-demo sequence

1. Deploy the compatible gateway and rengine readers first. The old v1-only gateway cannot read v2 captures.
2. Deploy the language trace-header responder and then the Python producer to the selected demo. These are additive response/request headers; no database migration is required.
3. Verify the installed language release matches Python's packaged fingerprint/runtime pin before sending the canary request.
4. Enable detailed capture through existing operator settings. Run the representative request and inspect Overview, Waterfall, service lanes, parent navigation, and raw evidence. A handler HTTP success must not be confused with fulfilled business intent.
5. Export the report using the existing audited export action. Validate the redacted export locally:

   ```sh
   node scripts/check-trace-rollout.mjs /absolute/path/to/redacted-export.json
   ```

   The checker requires a complete v2 report, completed terminal lifecycle, gateway→Python link, and both language/catalog remote-handler links with valid independent clock evidence. It prints counts and validation errors only, never report payloads. A request that legitimately skipped one boundary is not sufficient as this particular rollout canary.
6. Check a legacy saved report, refresh/deep links, live start→completion identity, tenant isolation, read/export permissions, and redaction. Verify malformed/missing trace headers do not change business responses.
7. Turn capture off, repeat the read-only request, and verify no new detailed report or downstream tracing headers are generated by Python. Existing operational telemetry and the gateway's small dispatch identifier remain independent of this switch.
8. Compare capture-on/off latency and report size against the agreed budget, including concurrency and event-limit pressure. Confirm terminal evidence is retained and incomplete captures are labeled. Approve the canary evidence before applying the same rollout to remaining demos.

## Rollback

Disable detailed capture using the existing setting if overhead or evidence quality fails acceptance. Revert the Python producer/language responder if necessary while retaining v1/v2-compatible readers so previously saved reports remain accessible. Do not delete or rewrite historical evidence. Recheck normal assistant behavior and capture-off mode before another canary.

## Production result — 2026-10-11

The compatible gateway readers and rengine Overview/Waterfall/service-lane UI are live on all four demos. Live checks passed for legacy v1 reports and journeys, tenant isolation, unauthenticated export denial, static modules and upstream readiness. All 94 gateway migration versions and checksums matched their databases; no schema migration was needed.

The candidate preserved the actual production dictionary and corpus. Validation passed: **230** affected Python tests, **29** real Python/Node contract checks, **61** rengine tests, and **136,372** archived language cases with zero semantic or wire failures. An isolated image canary also verified provenance, semantic cases and optional/malformed trace headers. This resolved the earlier local packaged-release fixture mismatch without weakening its guard.

Both grocery producer activations rolled back automatically on the capture-overhead gate. The larger retry used two warm-ups per mode and 20 measured samples per mode in alternating five-request blocks:

| Full-stream measurement | Result |
| --- | ---: |
| Capture-off p95 | 391.611 ms |
| Capture-on p95 | 695.560 ms |
| Acceptance limit: max(off × 1.25, off + 100 ms) | 491.611 ms |
| Outcome | Failed; producer restored |

The saved v2 canary was functionally correct: **23 events, three remote handlers**, complete terminal evidence and valid cross-service parent links. Functional correctness does not override the failed performance gate. These timings measure the rengine guest request through **HTTP stream EOF**, not storefront completion at the SSE `done` event. The storefront stops at `done`; the server also performs tracking persistence after turn completion. Profiling must separate those boundaries and identify the actual tail cost before changing the release acceptance criteria or producer code. No producer-code fix was made during these deployment attempts.

The expanded baseline reached the existing guest catalog quota (120 reads per 15 minutes). Probes stopped until its natural reset; no rate limit was changed or reset manually. The retry consumed a bounded 88 catalog reads in grocery and never advanced to other demos. Capture settings were restored. Coordinate future probes with other release work and retain quota headroom.

## Resumed rollout — revision 12 baseline

The separate knowledge revision 12 was preserved and the tracing candidate rebased onto release `eeeac359-a115-4df7-a9a7-e5ba310b8815`. Its runtime `7129ab9026be13189e7a1d23a4f7abbf1def680fbc11c6821ee082bd1529a65c` passed all **136,372** active archived cases on the production host; knowledge payloads stayed there. Candidate release `f8429ca4-e960-4756-8536-67d22ae99628` passed inactive HTTP/semantic checks. The staging runtime guard caught a stale helper image tag before release creation; it was corrected and revalidated.

The deployed rengine now reports `doneMs` and `postDoneMs` alongside unchanged full-stream `elapsedMs`. All **63** rengine tests pass. Local candidate checks passed **330 Python**, **29 wire**, **3 Node HTTP**, and **15 disposable PostgreSQL** tests, with copied-fixture corrections recorded in the artifact README.

Profiling established that a captured report's isolated durable save takes about **10 ms p95** locally. Live slow requests spend most of their delay before `done`, so changing to a completion-only gate or asynchronous persistence would not address the demonstrated tail.

An isolated same-host benchmark found the periodic Python/urllib health probe consumed about **366 ms CPU**; the equivalent Bash HTTP-status probe consumed **2.3 ms**. Node's built-in HTTP client reduced probe CPU from **122 ms to 60 ms**. The lightweight probes are deployed to all demos, preserving frequency, readiness endpoints, retries and outer timeouts, with unchanged CPU limits. Their exact commands pass **16 behavior tests**, including unhealthy/malformed/refused/timeout responses. This is a measured background-cost improvement, not a claim that tracing latency is fixed.

Two revision-12 canaries still failed and invoked rollback:

The jewelry slowest captured request had **14.8 ms after done**, with remaining CPU throttling observed. Further work must profile full-turn capture CPU under the real container limit before another activation. Do not retry an unchanged candidate repeatedly or lower the acceptance bar. The producer rollout remains incomplete; retained readers and health probes are independently verified improvements.
